# Проверка безопасности GitHub Pages

Проверка относится к статическому сайту `supernovvvvvachuu-droid/vibe-resale`: объявления читаются из GitHub Issues и добавляются к локальному каталогу. Повторная проверка выполняется на основе версии `9f457966227905f49106865a5b780f7ef0311221`; существующий дизайн не меняется.

## Обязательная модерация

До этого изменения `sellerItems` загружал открытые Issues без требования одобрения. Поэтому корректно заполненное объявление могло появиться в каталоге без ручной проверки владельца.

Теперь в `js/approval.mjs` и `js/listings.mjs` проверяются два условия: точная метка `approved` и служебная метка `review:…`, соответствующая текущему заголовку и полному тексту этого Issue. Запрос к API ограничен меткой `approved`, но каждый полученный элемент дополнительно проверяется: одного параметра запроса недостаточно для контроля доступа.

Отпечаток SHA-256 связывает проверку с именем репозитория, номером Issue, заголовком и текстом. Служебную метку нельзя перенести с другой вещи или репозитория. Она не является секретом: доверие опирается на права GitHub на изменение меток, а не на скрытие алгоритма.

Авторы обычных публичных Issues не получают прав менять метки. Участники с `triage` могут применять уже существующие метки, поэтому доступ к управлению метками тоже считается доверенным. Отпечаток не защищает от администратора, который меняет код, или от доверенного участника, повторно назначающего метки ранее проверенной неизменённой версии. Эти права не следует выдавать обычным продавцам.

Одна метка `approved` не защищала бы от замены описания автором после проверки. Поэтому новая версия текста отклоняется при несовпадении отпечатка, не дожидаясь реакции автоматизации. Задание `.github/workflows/moderate-listings.yml` снимает одобрение после редактирования, закрытия и повторного открытия Issue. Новое открытое объявление не одобряется автоматически.

При ручном добавлении `approved` автоматизация проверяет реальные права участника в репозитории (`write`, `maintain` или `admin`), а не доверяет полю `author_association`. Отпечаток берётся из снимка события одобрения. Текущее содержимое запрашивается повторно: если автор успел его заменить, задание не одобряет вместо владельца новый текст.

Сценарий автоматизации запускается из доверенной версии основной ветки, не исполняет команды из Issue и не подставляет пользовательское описание в shell. Права задания ограничены чтением кода и изменением Issues; пароль, личный токен или ключ от нового сервиса не требуются. Шаг checkout закреплён за конкретным коммитом официального действия, сохранение учётных данных отключено.

Инструкция владельцу: [MODERATION.md](MODERATION.md).

## Сохранённые исправления предыдущего аудита

1. **Проверялся уже изменённый адрес покупки** — `js/listings.mjs`, функция `readListing`. До проверки разрешённых адресов код вызывал `new URL`, затем удалял query и fragment. Такой порядок скрывал явный порт `:443`, кодирование имени хоста и параметры переадресации от строгой проверки `validatedExternalUrl`. Исправление: проверять исходную строку, принимать только прямые HTTPS-адреса разрешённых площадок, не исправлять опасный адрес молча.
2. **Ошибка одного элемента прерывала загрузку всех объявлений продавцов** — `js/listings.mjs`, функции `readListing` и `sellerItems`. Не проверялись типы `issue`, `title`, `body` и форма ответа API; один исключительный элемент прерывал `issues.map`. Основной статический каталог сохранялся благодаря `catch` в `js/api.mjs`, однако объявления остальных продавцов терялись. Исправление: проверять входную структуру и пропускать некорректные записи отдельно.
3. **Не было предела продолжительности загрузки** — `js/listings.mjs`, `sellerItems`. Цикл пагинации не имел верхней границы, а запросы — тайм-аута. Недоступный ответ или слишком большой поток Issues мог задержать показ каталога. Исправление: ограничить запросы по времени и числу страниц, безопасно обрабатывать ошибку источника.

Эти выводы не означают, что злоумышленник мог записать произвольный код в репозиторий через Issue: запись Issue и изменение файлов репозитория — разные права GitHub.

## Что уже сделано безопасно

- Название, описание, размер, состояние и подписи проходят экранирование `escapeHTML` в `js/core.mjs` и `e` в `js/components.mjs` / `js/views.mjs`. Пользовательский Markdown или HTML не вставляется как исполняемый HTML.
- Фотографии проходят `safeImagePath`; произвольные `javascript:`, `data:` и внешние трекеры не становятся `src` карточки.
- Страница вещи повторно проверяет адрес покупки через `validatedExternalUrl`. Внешняя вкладка открывается с `rel="noopener noreferrer nofollow"`.
- Единый список разрешённых контактных доменов ограничен `avito.ru`, `www.avito.ru` и `t.me`. Ранее в общей политике оставались дополнительные торговые площадки; они удалены по текущему требованию. Принимаются только прямые HTTPS-адреса, без учётных данных, портов, управляющих символов, сокращателей и параметров переадресации.
- Статический сайт не принимает пароль, платёжные данные или авторизационный токен для чтения публичного каталога. Публикация через Issues требует входа на стороне GitHub.

Безопасные участки не переписывались ради аудита.

## Проверки публичных файлов

Проверены отслеживаемые текстовые файлы, доступная локальная история репозитория и структура `catalog.json`. Поиск шаблонов приватных ключей, GitHub/OpenAI/Slack-токенов, AWS access keys и литералов JWT не обнаружил совпадений. Рекурсивная проверка каталога не выявила заполненных полей пароля, токена, CSRF, почты, идентификатора владельца или приглашения. В каталоге нет таблиц пользователей, сессий или служебных настроек. Имена фотографов и авторов шрифта относятся к публичным лицензионным сведениям.

Выражение `GITHUB_TOKEN` в workflow — обращение к временным учётным данным, которые GitHub выдаёт заданию во время запуска. Это не опубликованное значение токена. Браузер их не получает; автоматизация не должна печатать заголовки авторизации или пользовательские тела в лог.

Поиск по шаблонам не доказывает отсутствие любого возможного секрета. Если ключ когда-либо публиковался, одного удаления файла недостаточно: ключ нужно отозвать у его поставщика.

## Локальная проверка

Проверки находятся в `tests/`. Они используют локальные примеры и подменённый API GitHub, а не опубликованные тестовые объявления. Проверяются отсутствие одобрения, несовпадение отпечатка после правки, перенос меток между Issues, разрешённые и запрещённые контакты, права модератора, изменение текста во время одобрения и снятие меток автоматизацией. `tests/render-security.test.mjs` проверяет экранирование вредоносного текста в карточке и странице вещи, блокировку опасных `src` / `href`, рабочие ссылки Avito и Telegram, защиту `noopener` и сохранение подсчёта результатов тестов по стилю.

Запуск без сторонних зависимостей:

```sh
node --test --test-isolation=none tests/*.test.mjs
```

## Границы защиты GitHub Pages

У GitHub Pages нет прикладного сервера. Ручное решение и право изменять метки обеспечиваются GitHub, а автоматическое снятие одобрения и привязку к проверенному содержимому выполняет GitHub Actions. Посетитель проверяет эти данные при загрузке каталога; это не заменяет защиту прав доступа к самому репозиторию. Если Actions недоступен или проверка не завершена, публикация не открывается в обход проверки.

Неодобренная вещь скрыта из каталога, но сам Issue остаётся публичным на GitHub: это открытый репозиторий, а не закрытая очередь личных сообщений.

Уже открытая вкладка может сохранять ранее загруженную версию до обновления. Проверка отпечатка не отзывает ранее увиденное содержимое из памяти чужого браузера. Сайт не следует внешним ссылкам при проверке и не может гарантировать дальнейшее поведение Авито или Telegram. Такие гарантии не имитируются.

Отдельный сервер, платный хостинг и база данных не подключаются. Статические 16 вещей владельца в файлах репозитория остаются отдельным доверенным способом публикации, который требует прав на изменение кода; сторонний автор Issue не получает этих прав.

В исходной версии нет Content Security Policy. Совместимая политика могла бы дополнительно ограничить выполнение скриптов и источники загрузки, но её нельзя добавлять вслепую: фотографии вложений GitHub используют перенаправления на служебные CDN, а политика не должна ломать реальные изображения. HTTP-заголовки `frame-ancestors`, HSTS и `X-Frame-Options` также нельзя надёжно подменить HTML-метатегом.
