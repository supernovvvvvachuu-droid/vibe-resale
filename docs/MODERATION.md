# Ручная проверка объявлений

Посетитель смотрит каталог без регистрации. Продавец создаёт объявление в GitHub Issues, но само создание Issue не публикует вещь в каталоге.

Сам Issue в публичном репозитории виден на GitHub и до одобрения. Модерация управляет показом объявления в каталоге сайта, а не приватностью страницы GitHub.

## Как одобрить вещь

1. Откройте Issue с названием `Продам: …`.
2. Проверьте название, описание, настоящие фотографии, цену, размер, состояние и ссылку. Контактная ссылка должна вести прямо на HTTPS-страницу Авито или Telegram. Не одобряйте сокращатели, подозрительные переадресации и чужие фотографии.
3. В правой колонке Issue откройте **Labels** и добавьте метку **`approved`**. Это ручное решение владельца или доверенного участника с правами `write`, `maintain` или `admin`.
4. Дождитесь успешного задания **Actions → Moderate seller listings**. Оно добавит служебную метку, начинающуюся с `review:`. После этого корректное объявление сможет появиться в каталоге.

Если метки `approved` ещё нет, владелец может создать её через **Issues → Labels → New label**. Название должно быть именно `approved`, маленькими буквами.

Служебную метку `review:…` не нужно составлять, переносить или менять вручную. Она содержит отпечаток проверенного текста, а не пароль или секретный ключ. Одной метки `approved` без соответствующего отпечатка недостаточно для публикации.

## Что происходит после редактирования

Если автор меняет заголовок или описание, сохранённый отпечаток перестаёт совпадать с текущим объявлением. Сайт отклоняет такую версию даже в промежутке до запуска автоматизации GitHub. Затем задание снимает `approved` и служебные метки.

Чтобы вернуть вещь в каталог, снова проверьте все данные и заново добавьте `approved`. Автоматизация не одобряет изменённый текст вместо вас. Повторное открытие закрытого Issue тоже требует новой проверки.

Для старого объявления, у которого `approved` уже стояла до введения этой проверки, сначала проверьте содержание, затем снимите и заново добавьте метку. Старые объявления не получают одобрение автоматически.

Если страницу каталога уже открыли до правки, её нужно обновить: ранее показанное содержимое нельзя отозвать из памяти чужого браузера. Новая загрузка проверяет актуальную версию Issue.

## Если объявление не появляется

- Проверьте, что Issue открыт и название начинается с `Продам: `.
- Убедитесь, что есть `approved` и автоматическая метка `review:…`.
- Проверьте **Actions**: при отключённой автоматизации или ошибке задания публикация остаётся закрытой, проверки не обходятся.
- Проверьте поля объявления: цена должна быть положительным целым числом, фотография — вложением GitHub, контакт — допустимым прямым адресом Авито или Telegram.
- Если автор успел изменить текст во время проверки, повторите ручную проверку. Не переносите служебную метку с другой вещи.

Даже одобренное объявление проходит проверку адресов, структуры и безопасного отображения текста. Метка не разрешает исполнять HTML или JavaScript.

## Какие данные это затрагивает

Этот порядок относится к объявлениям продавцов из **GitHub Issues**. Ваши 16 вещей и 86 фотографий, уже добавленные непосредственно в файлы репозитория, остаются на сайте: их публикация управляется изменениями кода с правами владельца. Сторонний продавец через Issue не может изменить эти файлы.

GitHub Pages и существующий дизайн сохраняются. Отдельный сервер, платный хостинг и база данных не подключаются. Для автоматизации используется временный `GITHUB_TOKEN`, который GitHub выдаёт заданию сам: он не передаётся посетителям, не записывается в исходники и не требует создания личного токена продавца.

Права участников репозитория остаются важны: человек с правом менять код или настройки GitHub может изменить и правила публикации. Право `triage` тоже позволяет применять существующие метки — не выдавайте его случайным продавцам. Все, кто может менять код, настройки или метки репозитория, должны быть доверенными участниками; для обычного создания Issue эти права не нужны.
